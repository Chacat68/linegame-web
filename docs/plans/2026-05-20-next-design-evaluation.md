# 星际贸易商 - 后续设计评估与执行路线

> 日期：2026-05-20  
> 范围：探索情报、中期行动引导、商网 / 舰队经营、架构收口  
> 判定基准：以当前 `js/`、`tests/`、`docs/design/` 的实际接线为准。

---

## 1. 结论

当前项目已经完成核心单机经营版，并且探索 MVP 与前 30 分钟行动引导已经落地。后续设计的主线不应再是“补一个大系统”，而是：

**把探索获得的情报转化为经营决策，把行动引导从新手链扩展到中期链。**

这意味着下一阶段的设计中心是“中期经营闭环”：

```text
贸易获得资金
  -> 探索获得情报
  -> 情报影响市场 / 科研 / 派遣 / 商网
  -> 舰队与贸易站执行经营策略
  -> 公司成长解锁更高阶目标
```

---

## 2. 当前设计基线

### 已经可依赖的能力

- 贸易闭环：买入、航行、卖出、结算、供需变化。
- 经济与资本：价格历史、黑市、贷款、保险、股票、期货、贸易站投资。
- 探索 MVP：扫描、首次着陆、POI 调查、秘密航线、勘探报告。
- 行动引导 MVP：当前行动条、统一命令按钮、执行反馈、早期贸易 / 探索链建议。
- 中期系统骨架：舰队、船员、自动派遣、贸易站、科研、派系、任务、胜利路径。
- 工程基线：`SAVE_STATE_SCHEMA` 作为存档契约来源，Vitest 覆盖核心系统。

### 主要约束

- 项目仍是无构建的 Vanilla JS 静态站点，应避免引入大型框架迁移。
- `GameManager.js`、`MarketUI.js`、`MapUI.js` 体积已经较大，新增动作必须控制编排边界。
- 文本、任务和 UI 仍在快速变化，不适合立刻做完整 i18n。
- 单机主线尚未稳定到需要多人 / 云存档反向驱动架构。

---

## 3. 设计决策

### 决策 1：继续保持单机静态架构

短期继续维持 `localStorage + ES Modules + GameManager 编排`。只有当存档体积、跨设备同步或在线排行榜成为真实需求时，再启动 IndexedDB / 云存档 / 服务端设计。

取舍：

- 优点：迭代快，部署简单，测试成本可控。
- 代价：多人、云同步、跨端账号能力继续后置。

### 决策 2：行动引导扩展为中期建议层

继续复用 `GuidanceSystem -> ActionGuideUI -> GameManager` 的结构，不重做脚本化教程。新增建议必须是纯规则输出，不读 DOM，不直接改状态。

下一批建议优先覆盖：

- 科研补给：当前研究缺少资源或路线时，推荐市场 / 派遣动作。
- 派遣预填：根据船只、船员、勘探报告推荐可执行航线。
- 商网投入：发现高价值站点或资金闲置时，推荐投资 / 升级 / 派经理。
- 阻塞解除：燃料不足、船体受损、资金不足、事件待处理时，优先解除阻塞。

### 决策 3：勘探报告作为跨系统情报资产

探索结果不应只奖励积分或文字，而应沉淀为可被其他系统读取的情报资产。当前 `ExplorationSystem.getSurveyDecisionIntel()` 已经提供入口，后续应让它影响：

- 市场默认分区和推荐商品。
- 科研补给路线和研究完成节奏。
- 派遣评分与航线风险。
- 商网站点优先级、策略推荐和区域分工。

### 决策 4：商网二阶段优先做“轻物流”，暂不做完整模拟

不立即做复杂库存流、订单簿或玩家间市场。先在现有贸易站上加轻量经营层：

- 站点角色：采购、分销、科研补给、黑市前哨、物流中继。
- 区域收益：同区域站点形成加成。
- 情报加成：勘探报告可提高特定站点的收益或降低风险。
- 调度建议：行动条给出下一笔投入，而不是自动替玩家全权经营。

### 决策 5：新增中期动作前先拆 action handler 边界

`GameManager` 仍保留总编排职责，但不应继续承接所有细节。首批低风险拆分已经完成：

- `GuidanceActionController`：处理行动条 actionType 分发。
- `ExplorationActionController`：封装扫描、着陆、POI 的执行和反馈。
- `CommerceActionController`：封装商业终端导航、市场焦点和资本 / 经营入口跳转。

拆分原则仍是保持外部行为不变，先移动代码和测试，不做同时重构业务规则。后续新增 actionType 应继续进入 controller 边界，而不是回填到 `GameManager`。

## 4. 分阶段路线

## P0：文档与架构口径收口

目标：让所有后续设计基于同一事实。

- 更新实现对照表中的探索、行动引导、存档版本。
- 更新路线图，明确探索 MVP 已完成，下一阶段转为中期经营闭环。
- 更新架构文档，补充 `ExplorationSystem`、`GuidanceSystem`、`ActionGuideUI`、`CommandAction`。
- 建立新增建议规则：每条 suggestion 必须有优先级、reason、actionType、payload 和测试。

验收：

- 文档不再把扫描 / 着陆 / POI / 秘密航线写成未实现。
- 文档不再把旧 schema 版本写成当前版本。
- 新增中期功能时能直接引用本路线文档拆 issue。

## P1：行动引导二阶段

目标：让玩家在早期闭环后不迷路。

- 增加科研补给建议。（首批已落地：科研补给派遣预填）
- 增加派遣预填建议。（首批已落地：科研补给路线）
- 增加商网投入建议。（已落地：建站 / 单站升级 / 商网批量升级 / 批量增配入口）
- 增加阻塞解除建议。（首批已落地：待处理事件、低燃料补给、船体 / 维护度维修、科研补给资金不足）
- 增加资本侧建议。（首批已落地：贷款临期、期货临期 / 风险、股票观察位入口）
- 提取 `GuidanceActionController`，让 `GameManager` 只注入执行回调，不继续承载 actionType 分发细节。
- 给 `GuidanceSystem` 增加中期建议测试。

验收：

- 玩家完成初次交易和初探宇宙后，行动条能推荐至少一条中期目标。
- 有货、缺燃料、待处理事件、维修压力、资金不足时，建议优先解除当前阻塞。
- 金融 / 派遣 / 商网建议不会抢占未完成的贸易闭环。
- 市场 / 资本 / 经营入口的行动建议能落到正确子工作区。
- 已经打开目标市场分区时，导航型行动建议会自动让位给下一条建议，避免“查看行情”类循环。
- 科研补给之外的普通商运路线也能进入行动条，作为可预填的派遣策略建议。

## P2：探索情报联动

目标：让探索报告真正影响经营选择。

- 市场页读取勘探情报，调整默认 workspace 或 CTA。（首批已落地：行动引导可跳转市场情报区）
- 研究系统读取科研报告，给出补给或缩短研究的可解释反馈。
- 自动派遣评分吸收航线 / 后勤 / 市场报告。
- 商网站点候选列表展示本地勘探信号。（首批已落地：候选卡展示贸易窗口 / 补给节点 / 暗线航图 / 科研样本）

2026-05-24 收口状态：

- `ExplorationSystem.getSurveyDecisionIntel()` 已作为唯一归纳入口，稳定输出 `marketSignal`、`researchSignal`、`routeSignal`、`logisticsSignal`。
- 市场 / 商网：市场情报区、建站候选和策略推荐都能显示勘探报告带来的可解释信号。
- 科研：科研型报告会影响研究进度，并进入科研补给路线评分与 `strategySummary`。
- 派遣：普通派遣和科研补给派遣都会把勘探报告转成 `surveyIntelScore` 与 `surveyIntelSummary`。
- 收口测试已覆盖有报告 / 无报告时的显性差异，避免情报只成为隐藏数值加成。

验收：

- 同一星球在有 / 无勘探报告时，市场、科研、派遣或商网至少一个决策入口发生可解释变化。
- 报告影响以提示和评分呈现，不做不可见的黑箱加成。
- 每类报告至少有一条单元测试或集成测试覆盖。

## P3：商网二阶段轻物流

目标：把贸易站从被动收益点推进为中期经营目标。

- 给贸易站增加角色和区域标签。
- 增加区域组合收益。（首批已落地：同星系补给站 / 枢纽站 / 科研联络站组合给区域日收益加成，候选与已建站点均展示角色）
- 增加基于勘探报告的站点策略推荐。（已落地：候选 / 已建站点均展示建议策略，已建站点可一键切换）
- 在商业终端展示“下一笔最值得的商网动作”。（已落地：协同建站、升级、派经理、切策略、资金缺口提示）

2026-05-24 收口状态：

- 轻物流闭环已按“站点角色 + 区域协同 + 情报策略 + 下一笔动作”完成，不引入仓储、订单簿或完整物流仿真。
- 候选站点会同时暴露角色、建站后的区域组合收益、勘探报告驱动的策略建议和可执行建站动作。
- 商网下一步建议已覆盖协同建站、升级、派经理、切策略和资金缺口，能回答“现在最值得把钱投到哪里”。
- 回归用例已覆盖真实勘探报告进入建站候选、触发区域协同、给出策略推荐，并成为下一笔商网动作的同一条链路。

验收：

- 玩家能理解每个站点在商网里的定位。
- 公司资金有稳定去处。
- 商网决策能与探索、派遣、科研产生至少一种联动。

## P4：平台能力后置

基础短音效已经接入；背景音乐、音频资源包、动态音乐、i18n、云存档、多人、排行榜继续作为远期。只有当中期经营闭环稳定后，再评估是否进入平台层建设。

## 6. 不建议现在做

- 不做完整多人：当前价值低，架构成本高。
- 不做完整 i18n：文本和 UI 仍在变，先稳定内容结构。
- 不做完整音频系统：短提示音 MVP 已经够用，应等核心节奏稳定后再做背景音乐、资源包和动态音乐。
- 不做订单簿 / 玩家市场：会把单机经营模型推向另一套复杂经济系统。
- 不做大规模框架迁移：当前瓶颈是边界收口和中期闭环，不是框架能力。

## 7. 验证策略

每个中期设计进入实现前，应先补三类验证：

- 纯规则测试：输入 state 和 options，输出唯一 suggestion 或 intel。
- 系统联动测试：探索报告影响市场 / 科研 / 派遣 / 商网中的至少一处。
- UI 行为测试：行动条展示、按钮元信息、执行后反馈和刷新不残留。

当前基线命令：

```bash
npm test
```
