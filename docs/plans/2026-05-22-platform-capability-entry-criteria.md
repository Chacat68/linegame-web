# 平台能力进入条件评估计划

> 日期：2026-05-22  
> 目标：定义完整音频平台、i18n、云存档、多人、排行榜何时值得进入实现，避免过早分散中期经营闭环。  
> 架构：只制定进入条件和预备约束，不启动平台能力实现。  
> 技术栈：当前仍以静态站点、localStorage、ES Modules 为基线。

---

## 1. 当前基线

- 核心单机经营版已经可玩。
- 中期经营闭环仍在收口：探索情报、行动引导、商网轻物流。
- 基础短音效 MVP 已经接入：`AudioManager.js` 使用 Web Audio 程序化合成 UI、交易、航行和事件提示音，并通过设置持久化开关与音量。
- 背景音乐、音频资源包、动态音乐、分组混音等完整音频平台能力仍后置。
- i18n、云存档、多人、排行榜在多份设计文档中被列为后置。

## 2. 进入条件

- 完整音频平台：
  - 基础短音效反馈稳定，不再需要频繁调整 cue 类型与触发点。
  - 设置系统已有音效开关、音量控制和持久化位置。
  - 明确首批平台化范围是 BGM、音频资源加载或分组混音，不重复实现已存在的短音效 MVP。
- i18n：
  - 主要文案结构稳定。
  - 不再频繁调整市场、任务、行动条文本。
  - 能接受先做键值表，不做完整翻译平台。
- 云存档：
  - 存档 schema 连续两个迭代不破坏兼容。
  - 明确目标是跨设备同步，而不是多人。
  - IndexedDB / 远端 API 方案完成对比。
- 多人：
  - 单机经济模型稳定。
  - 明确是排行榜、异步市场还是实时协作。
  - 有服务端预算。
- 排行榜：
  - 胜利路径和评分口径稳定。
  - 能接受只上传匿名分数和版本号。

## 3. 实施步骤

1. 更新 `docs/design/MVP路线图.md`，把平台能力进入条件写入 P3 / P4。
2. 更新 `docs/design/09_技术架构设计.md`，说明当前不引入服务端。
3. 更新 `docs/design/设计实现对照表.md`，明确这些能力未实现且后置。
4. 为每项能力建立“进入前检查清单”，不写实现任务。
5. 每次中期经营闭环收口后复查一次。

## 4. 验收

- 后续讨论平台能力时能直接引用进入条件。
- 不会把完整音频平台、i18n、云存档、多人误当成当前版本缺陷，也不会把已落地的短音效 MVP 当成未开始。
- 当前实现仍聚焦中期经营闭环。
