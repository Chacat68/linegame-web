> 文档版本：1.0
>
> 文档状态：现行设计基线，待分阶段实施
>
> 更新日期：2026-07-16
>
> 适用范围：`linegame-web` 浏览器单机版全部运行时界面

## 0. 文档定位

本文档是《星际贸易商》交互 UI 的唯一现行设计标准，用于指导设计、开发、代码评审、视觉验收和后续功能扩展。

当本文档与以下旧文档发生冲突时：

- 交互 UI、HUD、终端、弹窗、表单、图表和响应式行为，以本文档为准。
- 飞船、星球、人物、场景等内容资产，继续参考 [`11_美术与视觉设计.md`](./11_美术与视觉设计.md) 与 [`美术风格指南.md`](./美术风格指南.md)。
- 游戏流程、系统规则与技术架构，继续以对应系统设计文档和当前代码实现为准。

本文档使用以下约束词：

- **必须**：上线前不可缺失。
- **应该**：默认遵守，仅在有明确理由时例外。
- **可以**：根据内容和性能条件选择使用。

### 0.1 核心边界

本轮 UI 重构默认遵守以下边界：

1. 不改变贸易、探索、任务、舰队、派遣、成长和存档规则。
2. 不改变业务状态含义，不新增或删除玩法字段。
3. 保留现有 DOM ID、事件入口和 `SurfaceManager` 生命周期契约，除非另有独立迁移方案。
4. 允许调整信息归属、排版、组件结构、样式类和可访问性属性。
5. 允许删除无行为、重复或纯噪音的 UI 元素，但必须先确认没有运行时引用。

## 1. 设计目标

### 1.1 产品体验目标

全局 UI 应形成一套“深空舰桥操作系统（Bridge OS）”视觉语言：冷静、精密、可信、可操作。玩家首先看到游戏世界和当前决策，其次才看到界面装饰。

设计必须同时满足：

- **清晰**：复杂经营数据能被快速扫描和比较。
- **一致**：相同状态、组件和操作在所有界面中表现一致。
- **高效**：常用任务路径短，主要操作清楚，反馈及时。
- **沉浸**：界面符合深空贸易世界观，但装饰不能损害可读性。
- **可扩展**：新功能能复用现有组件，而不是创建新的视觉分支。
- **可验证**：每条视觉和交互规则都能通过代码检查、测试或浏览器走查确认。

### 1.2 非目标

- 不以增加发光、扫描线、英文标签数量来制造科幻感。
- 不把桌面界面等比例缩小后直接作为移动端界面。
- 不为单个模块创建独立主题或新的按钮体系。
- 不用颜色作为状态的唯一表达方式。
- 不通过重复展示相同数据来提高“信息量”。

## 2. UI 宪章

所有新增和重构界面必须遵守以下规则：

1. **一个决策区域只有一个视觉主操作。**
2. **行动引导是唯一全局“下一步”提示。** 其他界面只展示局部状态、局部信号和可在本界面执行的动作。
3. **同一状态只有一个权威展示位置。** 其他位置只能显示为有明确上下文的摘要。
4. **同一屏最多使用两个强调色。** 状态色不计入品牌强调色，但必须克制使用。
5. **内容优先于容器。** 卡片、边框、网格和辉光用于组织信息，不得比内容更醒目。
6. **功能图标使用统一 SVG，内容图标可以使用 emoji。** 两者不得在同一语义层混用。
7. **所有交互必须有完整状态。** 默认、悬停、焦点、按下、禁用、锁定、加载和失败状态都必须可辨认。
8. **移动端采用重新编排。** 不允许只缩字号、缩间距或依赖横向溢出解决布局问题。
9. **新组件必须使用全局 Token。** 禁止在功能模块中重新定义品牌色、通用圆角或通用阴影。
10. **可访问性和性能属于完成标准。** 不是上线后的补充优化。

## 3. Surface 架构

### 3.1 分层模型

| 层级 | Surface | 典型界面 | 层级范围 | 行为规则 |
| --- | --- | --- | ---: | --- |
| L0 | Scene | 3D/2D 星图、背景 | `0–9` | 游戏世界主舞台 |
| L1 | Global Chrome | Header、Bottom Nav | `10–29` | 常驻，提供全局状态和一级导航 |
| L2 | Context HUD | HUD Rail、目标摘要、行动引导 | `30–59` | 与当前场景关联，可折叠 |
| L3 | Primary Workspace | 市场、完整星图工作区 | `60–79` | 同时只能打开一个 |
| L4 | Secondary Terminal | 机库、档案、日志 | `80–109` | 同时只能打开一个 |
| L5 | Non-blocking Feedback | Toast、事件通知 | `110–119` | 不阻塞输入，不覆盖关键 CTA |
| L6 | Blocking Modal | 交易确认、事件、剧情、派遣等 | `120–149` | 同时只能打开一个，必须锁定焦点 |
| L7 | Guided Overlay | 教程聚焦和强制引导 | `150–169` | 仅在明确引导流程中使用 |

### 3.2 互斥规则

- Primary Workspace 同时只能显示一个。
- Secondary Terminal 同时只能显示一个。
- 打开 Primary Workspace 时必须关闭所有 Secondary Terminal。
- 打开 Secondary Terminal 时必须关闭所有 Primary Workspace。
- Blocking Modal 同时只能显示一个；打开后必须隐藏非阻塞通知。
- Toast 和行动引导不得覆盖底部导航、主要操作和模态按钮。
- 关闭 Surface 后必须把焦点恢复到触发它的控件。
- 所有打开、关闭和焦点行为继续通过 `js/ui/SurfaceManager.js` 管理，功能模块不得绕过它自行修改通用显示状态。

### 3.3 Surface 尺寸

| 类型 | 桌面 | 平板 | 移动端 |
| --- | --- | --- | --- |
| Primary Workspace | 占据 `#game-main` 可用区域 | 占据主区域 | 全屏工作区 |
| Secondary Terminal | 最大 `1180 × 720`，四周保留安全边距 | `calc(100vw - 24px)` | `calc(100vw - 16px)`，接近全屏 |
| Small Modal | `360–440px` | `min(440px, 92vw)` | 底部 Sheet 或全宽卡片 |
| Medium Modal | `520–680px` | `calc(100vw - 32px)` | 全屏或近全屏 |
| Large Modal | `800–1040px` | `calc(100vw - 24px)` | 全屏 |

任何 Surface 都不得依赖 `left: 50%` 与固定宽高组合来保证可见性；必须同时受视口、安全区和内部滚动约束。

## 4. 视觉语言

### 4.1 风格定义

Bridge OS 使用“低装饰、高清晰、局部发光”的深色舰桥风格：

- 深黑蓝空间作为背景。
- 半透明终端表面用于组织功能区。
- 冷青色表达导航、焦点和可交互状态。
- 暖琥珀色表达商业机会、稀缺价值和重要提示。
- 绿色表达安全、成功和正向变化。
- 红色表达危险、失败和破坏性操作。
- 网格、扫描线、噪点和辉光只作为背景或局部反馈，不覆盖正文。

### 4.2 表面层级

| 表面 | 用途 | 视觉要求 |
| --- | --- | --- |
| Canvas | 星图和全局背景 | 最暗，不承载正文 |
| Shell | 终端和大型工作区 | 高不透明度、明确外轮廓 |
| Panel | 功能分组 | 与 Shell 有轻微明度差 |
| Card | 指标、列表项、局部动作 | 低对比边框，依赖间距分组 |
| Control | 按钮、输入框、Tab | 必须有清晰交互状态 |

每层只允许比上一层提高一个明度等级。禁止通过每层都增加双重边框和强辉光制造层次。

## 5. Design Token

### 5.1 颜色 Token

```css
:root {
  /* Background */
  --ui-bg-canvas: #02060b;
  --ui-bg-shell: rgba(3, 13, 22, 0.94);
  --ui-bg-panel: rgba(8, 24, 36, 0.86);
  --ui-bg-card: rgba(8, 28, 42, 0.72);
  --ui-bg-control: rgba(2, 10, 18, 0.92);
  --ui-bg-backdrop: rgba(0, 4, 10, 0.72);

  /* Text */
  --ui-text-primary: #edf8ff;
  --ui-text-secondary: #9ebaca;
  --ui-text-muted: #6f8796;
  --ui-text-disabled: #4f626d;
  --ui-text-inverse: #021018;

  /* Brand and semantic */
  --ui-accent: #6ce7ff;
  --ui-accent-strong: #9af0ff;
  --ui-commerce: #ffb86b;
  --ui-info: #3aa5ff;
  --ui-success: #57e39d;
  --ui-warning: #ffd166;
  --ui-danger: #ff7a68;

  /* Borders */
  --ui-line-subtle: rgba(108, 231, 255, 0.12);
  --ui-line-default: rgba(108, 231, 255, 0.20);
  --ui-line-strong: rgba(108, 231, 255, 0.42);
  --ui-line-warm: rgba(255, 184, 107, 0.36);
  --ui-line-danger: rgba(255, 122, 104, 0.42);
}
```

### 5.2 颜色使用规则

- `--ui-accent`：选中、焦点、当前导航、主要交互。
- `--ui-commerce`：商业机会、价格焦点、重要收益，不作为通用按钮色。
- `--ui-success`：成功、可领取、正向结果。
- `--ui-warning`：需要关注但尚未失败。
- `--ui-danger`：错误、损失、不可逆操作。
- 文本正文必须使用 `primary` 或 `secondary`；`muted` 仅用于辅助说明。
- 禁用状态不得只通过降低透明度表达，必须同时改变文字、边框和鼠标状态。

### 5.3 对比度

- 正文与背景对比度必须达到 `4.5:1`。
- 18px 以上大字号文本必须达到 `3:1`。
- 控件边界、焦点环和图标与相邻背景必须达到 `3:1`。
- 低对比装饰不得承载关键状态或可交互信息。

### 5.4 间距 Token

```css
:root {
  --ui-space-0: 0;
  --ui-space-1: 4px;
  --ui-space-2: 8px;
  --ui-space-3: 12px;
  --ui-space-4: 16px;
  --ui-space-5: 24px;
  --ui-space-6: 32px;
  --ui-space-7: 40px;
  --ui-space-8: 48px;
}
```

布局必须优先使用 Token。新增 `5px`、`13px`、`19px` 等孤立间距值需要在评审中说明理由。

### 5.5 圆角、边框和阴影

```css
:root {
  --ui-radius-control: 6px;
  --ui-radius-card: 10px;
  --ui-radius-panel: 16px;
  --ui-border-width: 1px;

  --ui-shadow-card: 0 10px 28px rgba(0, 0, 0, 0.28);
  --ui-shadow-panel: 0 24px 72px rgba(0, 0, 0, 0.54);
  --ui-focus-ring: 0 0 0 2px rgba(108, 231, 255, 0.18),
                   0 0 18px rgba(108, 231, 255, 0.16);
}
```

- 控件使用 6px，卡片使用 10px，大型 Surface 使用 16px。
- 常规卡片不使用外发光。
- 只有当前焦点、目标锁定和关键反馈可以使用局部辉光。
- 同一元素最多使用两层阴影。

### 5.6 尺寸 Token

```css
:root {
  --ui-control-sm: 30px;
  --ui-control-md: 36px;
  --ui-control-lg: 44px;
  --ui-icon-sm: 16px;
  --ui-icon-md: 20px;
  --ui-icon-lg: 24px;
}
```

- 桌面常规控件使用 36px。
- 触摸界面主要控件不得小于 44px。
- 纯图标按钮必须是正方形，并提供 `aria-label` 和 Tooltip。

## 6. 字体与排版

### 6.1 字体族

```css
:root {
  --ui-font-display: "Orbitron", "Rajdhani", sans-serif;
  --ui-font-interface: "Rajdhani", "PingFang SC", "Microsoft YaHei", system-ui, sans-serif;
  --ui-font-mono: "SFMono-Regular", Consolas, "Liberation Mono", monospace;
}
```

- Orbitron 仅用于品牌、英文终端代号、短 Kicker 和少量大数字。
- 中文标题、正文、按钮和表单统一使用 Interface 字体。
- 货币、百分比、时间、容量和价格比较使用等宽数字：`font-variant-numeric: tabular-nums`。

### 6.2 字号层级

| Token | 字号 / 行高 | 用途 |
| --- | --- | --- |
| Caption | `11 / 16px` | 时间戳、单位、辅助元数据 |
| Label | `12 / 16px` | 控件标签、Kicker、Badge |
| Body | `14 / 20px` | 正文、列表、按钮 |
| Body Strong | `14 / 20px` | 强调正文、关键数值说明 |
| Subheading | `16 / 22px` | 卡片标题、分区标题 |
| Title | `20 / 28px` | 终端标题、弹窗标题 |
| Display | `28 / 36px` | 极少量首屏主标题或关键数值 |

### 6.3 排版规则

- 中文正文不得使用全大写效果或过大的字距。
- 英文 Kicker 可以使用大写，但必须有中文主标题承担实际含义。
- 单行标签允许省略号；关键说明不得被无提示截断。
- 正文段落建议不超过 48 个中文字符宽。
- 列表卡标题最多两行；超过后必须提供详情入口或 Tooltip。
- 数值和单位之间使用一个半角空格，如 `1,000 CR`、`60 秒/天`。

## 7. 信息架构与唯一归属

| 信息 | 权威位置 | 允许的摘要 | 禁止行为 |
| --- | --- | --- | --- |
| 积分、位置、日期、当前舰船 | Header | 交易确认中显示交易前后积分 | 在机库和市场重复完整全局状态栏 |
| 燃料、护盾、货舱 | Header 舰船状态区 | 执行航行、补给、交易时显示关联值 | 在多个常驻 HUD 同时镜像 |
| 当前全局下一步 | Action Guide | 局部界面可以显示“局部信号” | 市场、HUD、机库分别给出竞争性下一步 |
| 当前目标 / 航点 | Target Intel / 星图详情 | Header 显示当前位置 | 多张详情卡同时作为主目标 |
| 完整市场数据 | Market Workspace | HUD 只显示一条市场摘要和入口 | HUD 中复制完整行情与执行操作 |
| 舰队与公司经营 | Hangar Terminal | Header 显示当前舰船身份 | 机库重复日期、全局导航和完整积分条 |
| 任务、科技、派系、成就 | Archive Terminal | HUD 只显示首要摘要、数量和入口 | 多个常驻任务列表并存 |
| 历史反馈 | Logs Terminal | Toast 显示短时结果 | Toast 长期占据主操作区域 |

摘要必须满足至少一个条件：

- 能直接跳转到权威界面。
- 与当前动作的成本、结果或风险直接相关。
- 是当前场景必须持续可见的状态。

## 8. 组件规范

### 8.1 按钮

按钮分为：

- **Primary**：当前决策区域的主要动作。
- **Secondary**：可选操作、返回、取消。
- **Ghost**：工具类或低优先级动作。
- **Danger**：不可逆或高损失动作。
- **Icon**：单一图标操作。

规则：

- 一个决策区域同时只能有一个 Primary。
- 危险操作不得使用 Primary 青色。
- 按钮文本使用动词或“动词 + 对象”，如“接取任务”“购买燃料”“确认交易”。
- 禁用按钮必须提供不可用原因；成长锁定应使用 Locked 状态，而不是普通 Disabled。
- 加载状态保持按钮宽度不变，并阻止重复提交。
- 图标按钮不得使用图标作为唯一可访问名称。

### 8.2 Tab 与分段导航

- 一级 Tab 用于同一终端内的平级模块。
- 二级 Tab 用于同一工作流的视图切换。
- 不允许出现三级常驻 Tab；应改用筛选器、Disclosure 或独立详情。
- Tab 必须支持方向键切换、`aria-selected`、`aria-controls` 和可见焦点。
- 移动端 Tab 可以横向滚动，但当前项必须自动进入可视区域。
- 锁定 Tab 可以可见，但必须显示解锁条件并不可被选中。

### 8.3 Card

Card 分为：

- **Metric Card**：一个指标、一个数值、一句解释。
- **Entity Card**：商品、舰船、任务、科技等对象。
- **Action Card**：包含明确局部操作。
- **Status Card**：成功、风险、锁定、空状态。
- **Preview Card**：从摘要跳转到完整界面的预览。

规则：

- 卡片不能为了视觉完整而重复已有全局信息。
- 可点击卡片必须整卡可聚焦，并提供 Hover、Focus 和 Active 状态。
- 卡片内超过两个操作时，应设置一个主操作，其余放入次级区域或菜单。
- 不允许嵌套超过两层卡片。

### 8.4 Badge、Chip 与状态标签

- Badge：数量、未读、待领取等短状态。
- Chip：筛选条件、属性、分类、轻量状态。
- 不使用全尺寸按钮样式模拟不可点击 Chip。
- 状态标签必须包含文字，不得只显示颜色圆点。
- Badge 数值超过 99 时显示 `99+`。

### 8.5 表单控件

- Input、Select、Range、Toggle 使用统一高度和焦点环。
- Label 必须始终可见；Placeholder 不能替代 Label。
- 错误信息放在控件下方，并通过 `aria-describedby` 关联。
- 数值输入必须声明单位、范围和步进。
- Toggle 必须同时有文字状态，不得只靠滑块位置表达开关。
- 破坏性设置必须与常规设置分区，并使用 Danger 样式。

### 8.6 Meter、Progress 与数值状态

- Meter 表示当前资源水平，如燃料、护盾、货舱。
- Progress 表示任务、研究、等级等完成进度。
- 两者必须同时提供文本数值，不得只显示色条。
- 阈值变化必须同时使用颜色和文字，如“燃料不足 12%”。
- 进度动画只在数值发生变化时播放一次。

### 8.7 Table 与列表

- 数字列右对齐，名称列左对齐。
- 表头在长列表中应该 Sticky。
- 行 Hover 只用于可交互或可选行。
- 移动端优先把表格转换为摘要卡片；仅在数据对比价值高时允许横向滚动。
- 列表必须有空状态、加载状态和错误状态。

### 8.8 Empty、Loading、Error

Empty State 必须包含：

1. 当前为什么没有内容。
2. 玩家是否能采取行动。
3. 如果能，提供一个明确入口。

Loading State：

- 不改变已知容器尺寸，避免布局跳动。
- 小于 300ms 的操作不显示加载动画。
- 超过 300ms 使用局部进度或 Skeleton；不得用全屏阻塞遮罩替代局部加载。

Error State：

- 使用简明中文说明发生了什么。
- 提供安全的重试、返回或关闭操作。
- 不在玩家界面显示内部异常堆栈。

### 8.9 Tooltip

- 用于解释图标、缩写、复杂指标或不可用原因。
- 不能承载完成任务所必需的唯一信息。
- 键盘聚焦与悬停都必须触发。
- 移动端依赖点击或长按的 Tooltip 必须有替代可见文本。

### 8.10 Toast 与通知

| 等级 | 用途 | 默认持续时间 | 是否进入日志 |
| --- | --- | ---: | --- |
| Info | 普通状态更新 | 3 秒 | 可选 |
| Success | 操作成功 | 3 秒 | 是 |
| Warning | 风险、资源不足 | 5 秒 | 是 |
| Error | 操作失败 | 6 秒或手动关闭 | 是 |

- 同时最多显示三条 Toast。
- 相同消息短时间重复出现时必须合并计数。
- Toast 不提供复杂决策；需要决策时使用 Modal。
- Blocking Modal 打开时暂停或隐藏非关键 Toast。

### 8.11 Modal

所有 Modal 使用统一结构：

```text
Modal Backdrop
└── Modal Box
    ├── Header：Kicker、标题、关闭
    ├── Body：内容、摘要、表单或选项
    └── Footer：Secondary、Primary / Danger
```

规则：

- 必须有清晰标题和可访问描述。
- 必须锁定键盘焦点，并在关闭后恢复焦点。
- `Escape` 默认关闭；高风险执行过程中可以临时禁止，但必须提供可见状态。
- 点击 Backdrop 是否关闭由内容风险决定，不能在模块中随意变化。
- 主要确认按钮位于 Footer 右侧；移动端可以全宽。
- 交易、删除存档、重置等操作必须在执行前展示结果或影响摘要。

### 8.12 Terminal Shell

机库、档案、日志以及设置界面的内部视觉结构必须共用 Terminal Shell：

```text
Terminal Shell
├── Header：终端代号、中文标题、说明、模块状态、关闭
└── Body
    ├── Sidebar / Mobile Tabs
    └── Content：Summary、Primary Content、Local Actions
```

- Header 高度、关闭按钮、边框、背景和滚动规则必须一致。
- Sidebar 只用于模块导航和必要摘要，不复制全局状态栏。
- Content 内只有一个主滚动容器。
- 移动端将 Sidebar 转换为顶部 Tabs 或可折叠摘要。
- 设置界面只复用 Terminal Shell 的视觉结构，生命周期仍属于 Blocking Modal，必须保持焦点锁定和 `aria-modal="true"`。

## 9. 图标规范

### 9.1 图标分类

| 类型 | 技术形式 | 示例 |
| --- | --- | --- |
| 功能图标 | 单色 SVG | 设置、关闭、返回、筛选、导航 |
| 状态图标 | SVG + 状态色 | 成功、警告、错误、锁定 |
| 内容图标 | Emoji 或内容资产 | 商品、人物、星球、舰船、成就 |
| 品牌符号 | SVG / CSS 图形 | Logo、终端标识 |

### 9.2 SVG 规则

- 使用 `16 / 20 / 24px` 三档视口尺寸。
- 默认描边 1.5px，统一圆角端点和连接。
- 使用 `currentColor`，不得在 SVG 内硬编码功能色。
- 相同含义必须复用同一图标。
- 纯装饰 SVG 使用 `aria-hidden="true"`。

### 9.3 Emoji 规则

- Emoji 只表示游戏内容，不表示通用界面操作。
- Emoji 后必须有文字名称，不得作为唯一识别信息。
- 装饰性 Emoji 必须从无障碍树隐藏。
- 同一实体的 Emoji 必须由数据层统一提供，不在 UI 模块中重复硬编码。

## 10. 文案与术语

### 10.1 语言层级

- 中文承担所有关键含义。
- 英文只作为品牌、终端代号和短 Kicker。
- 禁止出现只有英文、没有中文解释的关键状态。
- 中英文同时出现时，英文是次级信息，字号和对比度低于中文主标题。

### 10.2 文案语气

- 使用舰桥系统式、简洁、客观的语气。
- 状态描述优先说明事实，再说明影响。
- 操作按钮使用明确动词。
- 避免连续出现“建议、推荐、下一步、优先”等竞争性引导词。
- 全局行动使用“当前行动”；局部信息使用“信号、状态、可升级项、待处理”。

### 10.3 术语基线

| 概念 | 标准用语 | 禁止混用 |
| --- | --- | --- |
| 玩家货币 | 积分 / `CR` | 金币、资金、信用点并存 |
| 当前地点 | 当前航点 | 位置、节点、站点无上下文混用 |
| 货舱使用量 | `已用/总量` | 容量、库存、载重无解释切换 |
| 未达到开放条件 | 未解锁 | 锁死、禁用、不可用混用 |
| 暂时没有数据 | 暂无… | 空、无、未开放混用 |
| 全局引导 | 当前行动 | 下一步建议、推荐动作多处出现 |

功能模块如需使用专业术语，必须在首次出现时提供解释或 Tooltip。

### 10.4 数字格式

- 货币：`1,000 CR`。
- 百分比：`+12.5%`、`−4.0%`。
- 容量：`12/40`，必要时补充单位。
- 等级：`Lv.3`。
- 天数：`第 12 天`。
- 时间：短时使用“2 分钟”，长时使用“3 天”。
- 小数位必须由业务精度决定，同类指标保持一致。

## 11. 数据可视化

### 11.1 通用规则

- 图表必须有标题、时间范围、单位和当前值。
- 正向变化使用绿色，负向变化使用红色；同时显示 `+ / −` 和方向箭头。
- 不使用颜色作为唯一编码，必须配合形状、图标、纹理或文字。
- 网格线保持低对比，不能高于数据线。
- 同一页面中最多突出一条主数据序列。
- Tooltip 必须显示横轴值、纵轴值和单位。

### 11.2 市场图表

- 当前货物颜色使用 `--ui-commerce` 或内容分类色。
- 均线、价格区间和供需信号必须有固定图例。
- 涨跌榜、波动榜和 K 线使用一致的正负语义。
- 图表与执行按钮必须共享同一个“当前选中货物”状态。
- 移动端优先展示当前价格、趋势和执行动作，完整指标可折叠。

### 11.3 指标卡

- 一张卡只突出一个主数值。
- 单位、时间范围和变化值不能与主数值竞争。
- 变化值必须说明比较基准，如“较昨日”“近 7 天”。
- 没有可靠趋势时显示“数据不足”，不得用 `0%` 假装稳定。

## 12. 页面与工作区规范

### 12.1 Header

职责：全局身份、全局经济状态、当前位置、日期和当前舰船状态。

- 桌面高度建议 72px，平板 60px，移动端 52px。
- 左侧为品牌和身份，中部为权威状态，右侧为全局工具。
- 不在 Header 中显示局部任务或市场建议。
- 移动端优先保留积分与全局工具；被收起状态必须有统一入口查看。
- 文本过长使用省略号，完整内容通过 Tooltip 或详情界面查看。

### 12.2 星图

星图是游戏主舞台，必须始终是首要视觉元素。

- 地图节点、航线和选中目标的对比度高于背景网格。
- HUD Rail 只承担导航、摘要和轻量控制。
- 同时只能有一个主详情焦点：目标预览、星球详情或扫描结果。
- 行动引导固定在底部导航上方，不遮挡地图主要操作。
- 银河模式与局部星图模式使用相同控件位置和状态反馈。

### 12.3 市场

市场是 Primary Workspace，不使用普通居中弹窗定位。

桌面推荐结构：

```text
Market Header / Context Bar
├── 左：价格趋势与当前货物
├── 中：商品执行列表
└── 右：行动摘要与市场信号
```

规则：

- 首屏先展示当前货物、买卖价格、货舱、资金和主要执行按钮。
- 成长路线、锁定模块和长期经营入口进入次级区域。
- 商品列表、图表和快速交易必须共享选中状态。
- 远程市场必须明确标记只读状态和可执行条件。
- 移动端顺序为：当前货物 → 执行 → 图表 → 商品列表 → 辅助情报。

### 12.4 机库

- 使用统一 Terminal Shell。
- Sidebar 展示公司权限、模块导航和必要局部摘要。
- 主内容优先展示当前舰船、编队状态和可执行操作。
- 舰船燃料、维护和货舱只在与管理操作相关时重复展示。
- 改装、人员和派遣作为舰船局部动作，不与全局行动引导竞争。
- 移动端关闭按钮必须进入 Header，禁止单独占据一整行。

### 12.5 档案

- 使用统一 Terminal Shell。
- 任务、科技、派系、成就是同级模块。
- 每个模块首屏包含摘要、主要内容和局部待处理项。
- Badge 只显示真实待处理数量。
- 任务界面可以显示局部推进状态，但不得重新定义全局下一步。

### 12.6 设置

- 设置是 Blocking Modal，内部使用 Terminal Shell 的系统变体；不得改成可与游戏场景同时操作的 Secondary Terminal。
- 模块分为显示、游戏、数据；危险操作单独分区。
- 当前值必须在控件附近可见。
- 设置变更自动保存时必须有轻量反馈。
- 恢复默认、重置教程、清除存档必须清楚区分风险等级。

### 12.7 日志

- 日志必须是可见、可访问的 Secondary Terminal，而不是只有导航激活状态。
- 提供时间、类型、摘要和未读状态。
- 支持全部、交易、航行、任务、系统、错误等基础筛选。
- 新消息自动进入日志；打开日志后清除未读 Badge。
- 相同短时消息可以聚合，但不得丢失关键错误和交易结果。

### 12.8 行动引导

- 是唯一全局“下一步”入口。
- 必须包含：上下文、动作标题、简短原因、执行按钮。
- 默认文案不超过两行。
- 执行中保持位置稳定，完成后使用短反馈并自动回到下一条行动。
- 移动端使用两行布局，执行按钮不得被折叠控件挤压。

### 12.9 阻塞弹窗

- 交易、事件、剧情、派遣、改装、船员、设置、胜利等弹窗共用 Modal 规范。
- 操作前展示必要成本、风险和结果摘要。
- 选项超过五项时使用可滚动 Body，Footer 保持可见。
- 复杂内容在移动端改为全屏，不强行保留桌面宽高比。

## 13. 组件状态矩阵

| 状态 | 视觉 | 交互 | 文案要求 |
| --- | --- | --- | --- |
| Default | 中性表面与边框 | 可操作 | 使用动作名称 |
| Hover | 轻微提亮 | 鼠标可操作 | 不新增必要信息 |
| Focus | 明确焦点环 | 键盘可操作 | 与 Hover 同等完整 |
| Active | 主色边框或底色 | 当前按下/展开 | 可显示当前状态 |
| Selected | 稳定高亮 | 当前选中 | 必须可通过 ARIA 读取 |
| Disabled | 降低对比、无指针 | 不可操作 | 必要时解释原因 |
| Locked | 锁定图标、条件提示 | 不执行主动作 | 显示解锁条件 |
| Loading | 保持尺寸、局部进度 | 阻止重复提交 | 使用进行时文案 |
| Success | 绿色 + 图标 + 文字 | 可继续 | 明确完成结果 |
| Warning | 黄色 + 图标 + 文字 | 可以继续或修正 | 明确风险 |
| Error | 红色 + 图标 + 文字 | 提供重试/返回 | 说明发生了什么 |
| Empty | 中性插图或图标 | 可选引导动作 | 说明原因和下一入口 |
| Claimable | 成功色 Badge | 可领取 | 明确奖励和领取动作 |

Disabled 与 Locked 不能混用：Disabled 表示当前不可执行，Locked 表示需要达成明确成长条件。

## 14. 交互与导航

### 14.1 指针与键盘

- 所有鼠标可点击操作必须可通过键盘完成。
- 可交互元素必须使用语义化元素或正确角色。
- Tab 顺序必须符合视觉顺序。
- Tab 组件使用方向键切换；Escape 关闭当前可关闭 Surface。
- Enter / Space 激活按钮和可点击卡片。
- 星图画布需要独立键盘替代路径访问关键节点和操作。

### 14.2 焦点管理

- 打开 Primary Workspace 后，焦点进入标题或首个主要控件。
- 打开 Secondary Terminal 后，焦点进入当前选中的 Tab 或内容标题。
- 打开 Blocking Modal 后，焦点进入首个决策控件。
- 关闭后恢复到原始触发元素。
- 焦点不可落入隐藏、`inert` 或 `aria-hidden="true"` 的内容。

### 14.3 确认规则

仅以下操作需要确认：

- 不可逆操作。
- 会造成显著资源损失的操作。
- 玩家可能因误触而产生难以恢复后果的操作。
- 清除存档、重置、放弃关键进度。

普通导航、筛选、折叠、低成本操作不使用确认弹窗。

## 15. 动效规范

### 15.1 时间与曲线

```css
:root {
  --ui-motion-fast: 120ms;
  --ui-motion-control: 160ms;
  --ui-motion-panel: 220ms;
  --ui-motion-slow: 320ms;
  --ui-ease-standard: cubic-bezier(0.2, 0, 0, 1);
  --ui-ease-enter: cubic-bezier(0.16, 1, 0.3, 1);
  --ui-ease-exit: cubic-bezier(0.4, 0, 1, 1);
}
```

- 控件反馈：120–160ms。
- Surface 进入：180–220ms。
- Surface 退出：120–180ms。
- 复杂状态变化不得超过 320ms。
- 优先动画 `opacity` 和 `transform`，避免动画布局属性。

### 15.2 动效等级

项目沿用三档设置：

| 模式 | 行为 |
| --- | --- |
| Full | 完整转场、局部辉光和非必要氛围动效 |
| Reduced | 保留必要状态反馈，移除大幅移动、循环扫描和强模糊 |
| Off | 关闭非必要动画，状态立即切换 |

- 必须同时尊重 `prefers-reduced-motion` 与项目内 `data-motion` 设置。
- 动效关闭后，状态仍必须通过颜色、边框、图标和文字完整表达。
- 无限循环动画只允许用于真正持续运行的状态，且不得大面积出现。

### 15.3 模糊与辉光预算

- 同屏最多一个大面积 `backdrop-filter` Surface。
- 移动端和低性能模式优先关闭大面积模糊。
- Canvas 本身不应因打开普通 HUD 而执行高成本模糊；可以使用变暗遮罩。
- 卡片列表不使用逐项滤镜动画。

## 16. 响应式规范

### 16.1 断点

| 名称 | 范围 | 主要策略 |
| --- | --- | --- |
| Compact | `≤ 560px` | 单列、触摸优先、接近全屏 Surface |
| Mobile / Small Tablet | `561–760px` | 单列或双列、顶部 Tab |
| Tablet | `761–1023px` | 双列、收窄 Sidebar |
| Desktop | `≥ 1024px` | 多栏、完整 Header 和 Terminal |

高度低于 620px 时必须同时触发低高度适配，不能只按宽度判断。

### 16.2 验收视口

所有重要界面至少覆盖：

- `1440 × 900`
- `1280 × 800`
- `1024 × 768`
- `768 × 1024`
- `390 × 844`

### 16.3 通用规则

- 必须使用 `viewport-fit=cover` 和 safe-area Token。
- 页面 Body 不滚动；Surface 内部只有一个主滚动容器。
- 底部导航、Sticky CTA 和系统安全区不得重叠。
- 触摸目标至少 `44 × 44px`。
- 移动端正文不得小于 13px，主要按钮不得小于 14px。
- 不允许关键操作依赖 Hover。

### 16.4 组件转换

| 桌面组件 | 移动端转换 |
| --- | --- |
| 固定 Sidebar | 顶部 Tabs 或折叠摘要 |
| 三栏工作区 | 按决策顺序的单列流 |
| 大型居中 Modal | 全屏 Modal / Bottom Sheet |
| 宽表格 | 摘要卡片；必要时横向滚动 |
| Header 完整状态 | 核心状态 + 统一详情入口 |
| 行内操作组 | 主操作全宽，次级操作折叠或换行 |

## 17. 无障碍规范

### 17.1 基线

- 目标标准：WCAG 2.1 AA。
- 所有功能必须可键盘操作。
- 所有可交互元素必须有可访问名称。
- 所有图表、Meter 和 Progress 必须有文本替代。
- 所有错误必须通过文字说明，并与相关控件关联。
- 所有状态变化必须在必要时通过 `aria-live` 宣告。

### 17.2 颜色与认知

- 不以红绿颜色作为唯一涨跌或成功失败编码。
- 闪烁频率不得超过每秒 3 次。
- 避免连续大写英文、过小字号和长段低对比文字。
- 复杂面板必须有清晰标题、分区和阅读顺序。

### 17.3 Modal 与 Terminal

- Blocking Modal 使用 `aria-modal="true"`。
- Secondary Terminal 使用适当的 `role="dialog"` 或 `region`，并维护 `aria-hidden`。
- 标题通过 `aria-labelledby` 绑定，描述通过 `aria-describedby` 绑定。
- 隐藏 Surface 不得保留可聚焦子元素。

## 18. CSS 与前端实现规范

### 18.1 Cascade 层级

新样式按以下顺序组织：

```css
@layer reset, tokens, base, primitives, layout, surfaces, features, utilities;
```

- `tokens` 是全局颜色、字号、间距和层级的唯一来源。
- `primitives` 定义按钮、表单、卡片、Badge 等基础组件。
- `surfaces` 定义 Workspace、Terminal、Modal、Toast。
- `features` 只定义市场、机库、档案等业务布局。
- `utilities` 只包含单一职责工具类。
- 不新增永久性的 `override` 层。

### 18.2 选择器规则

- 新组件类使用 `ui-` 前缀，如 `.ui-button`、`.ui-card`、`.ui-terminal`。
- 功能模块使用模块前缀，如 `.market-`、`.hangar-`、`.archive-`。
- 状态优先使用 `data-state`、`aria-selected`、`aria-expanded` 或 `.is-*`。
- DOM ID 主要用于 JavaScript 和可访问性关联，不作为新组件样式主选择器。
- 新样式选择器特异性原则上不超过三个类。
- 除显示工具类、第三方覆盖和明确的迁移边界外，不使用 `!important`。

### 18.3 文件职责

建议目标结构：

```text
css/
├── tokens.css
├── base.css
├── primitives.css
├── layout.css
├── surfaces.css
├── responsive.css
├── map.css
├── market-terminal.css
├── hangar-terminal.css
├── archive-terminal.css
├── settings.css
├── modals.css
└── utilities.css
```

- 单个功能样式文件超过约 1,200 行时，应该按 Surface 或职责拆分。
- 禁止在文件末尾持续追加“最终覆盖”“临时修复”区段。
- 删除旧规则前必须通过 `rg` 确认选择器引用，并完成相关界面走查。

### 18.4 DOM 与业务契约

- UI 重构必须保留业务模块依赖的 ID、`data-*`、ARIA 关系和事件入口。
- UI 模块不得直接修改核心游戏状态，应继续通过 GameManager 注入的回调执行操作。
- Surface 显示、互斥、焦点和关闭行为必须继续通过 SurfaceManager。
- 动态 HTML 必须转义玩家可控和存档来源文本。

---

## 19. 性能规范

- 目标桌面交互帧率 60fps；低性能模式不得低于可操作水平。
- 动画只使用 `opacity`、`transform` 等合成友好属性。
- 避免对大型列表逐项使用阴影、模糊和持续动画。
- 同屏大面积模糊层不超过一个。
- 动态列表更新优先复用容器，避免无必要全量重建和布局抖动。
- 可延迟的功能样式继续按需加载，但加载顺序必须可预测。
- 字体加载失败时必须使用系统字体正常显示，不能阻塞界面。
- UI 图标优先使用内联 SVG symbol 或可缓存资源，不重复嵌入大量相同 SVG。

## 20. 测试与视觉验收

### 20.1 自动化检查

每个 UI 批次至少执行：

```bash
npm test
npm run build
git diff --check
```

涉及 Surface、焦点和响应式时，必须保留或补充以下测试类型：

- Surface ID、角色和 ARIA 契约。
- Primary / Secondary / Blocking 互斥。
- 打开后的初始焦点和关闭后的焦点恢复。
- Tab 键和方向键行为。
- 行动引导两行布局和窄屏约束。
- Header、Bottom Nav、Toast 和 CTA 的安全区约束。
- Locked、Disabled、Loading、Empty、Error 状态。

### 20.2 视觉回归矩阵

| 界面 | 必测状态 |
| --- | --- |
| 星图 | 默认、目标选中、扫描结果、银河模式、HUD 展开 |
| 市场 | 现货、行情、远程只读、锁定模块、交易确认 |
| 机库 | 舰队、商店、改装、船员、派遣 |
| 档案 | 任务、科技、派系、成就、待领取 |
| 设置 | 显示、游戏、数据、危险操作 |
| 日志 | 默认、筛选、未读、空状态 |
| 弹窗 | 交易、事件、剧情、确认、失败、胜利 |
| 引导 | 默认、执行中、完成、折叠、窄屏 |

每个重要状态至少保留 `1440 × 900` 和 `390 × 844` 两张基准截图。

### 20.3 人工走查

- 页面加载后主要内容清晰可见。
- 当前页面、当前目标和主操作在 3 秒内可识别。
- 无 Surface 落在视口外。
- 无正文、按钮和导航被遮挡。
- Body 不产生意外滚动条。
- 键盘可以打开、操作并关闭界面。
- 焦点环清晰且顺序合理。
- 动效 Reduced / Off 模式功能完整。
- 低性能模式没有大面积模糊和明显卡顿。

## 21. 分阶段迁移策略

### Phase 0：冻结基线

- 建立当前 Surface 清单和截图基线。
- 确认现有 DOM、测试和业务入口。
- 标记重复 Token、重复选择器和失效样式。

### Phase 1：Token 与 Primitive

- 建立单一 Token 文件。
- 实现 Button、Icon Button、Tab、Card、Badge、Input、Meter、Empty State。
- 保留旧模块外观，先完成基础组件接入。

### Phase 2：Global Chrome 与星图

- 统一 Header、HUD Rail、Action Guide、Bottom Nav。
- 明确信息唯一归属。
- 完成五组视口适配。

### Phase 3：Workspace 与 Terminal

- 优先重构市场，解决桌面越界和信息密度。
- 让机库、档案、设置和日志接入统一 Terminal Shell。

### Phase 4：Modal 与反馈

- 统一全部阻塞弹窗。
- 统一 Toast、事件通知、加载、错误和空状态。

### Phase 5：清理与收口

- 删除旧 Token、重复规则和最终覆盖区段。
- 完成全量测试、构建、截图和人工走查。
- 更新相关设计文档中的旧 UI 口径。

每个阶段必须是可运行、可测试、可回退的独立批次，不允许先同时破坏全部界面再集中修复。

---

## 22. Definition of Done

一个 UI 功能只有同时满足以下条件才算完成：

- [ ] 使用全局 Token，没有创建新的通用色、圆角和阴影。
- [ ] 复用了现有 Primitive 或说明了新增组件的必要性。
- [ ] Default、Hover、Focus、Active、Disabled / Locked、Loading、Error 状态完整。
- [ ] 信息归属符合本规范，没有制造新的常驻重复信息。
- [ ] 主操作清晰，没有与行动引导竞争全局下一步。
- [ ] 桌面、平板和移动端布局已定义。
- [ ] 键盘、焦点恢复、ARIA 和 Reduced Motion 已验证。
- [ ] 没有引入不必要的 `!important` 和覆盖链。
- [ ] 相关自动化测试通过。
- [ ] 五组验收视口无越界、遮挡和错误滚动。
- [ ] 视觉截图与基线差异已审阅。
- [ ] 未改变玩法、状态和存档契约，或变更已由独立设计批准。

## 23. 评审清单

设计评审时依次回答：

1. 玩家进入界面后第一眼应该看到什么？
2. 当前唯一主操作是什么？
3. 哪些信息是权威数据，哪些只是摘要？
4. 是否使用了现有组件和状态？
5. 锁定、加载、空、错误和成功状态是什么样？
6. 键盘和触摸如何完成同一任务？
7. 390px 宽度下组件如何重新编排？
8. Reduced Motion 和低性能模式会关闭什么？
9. 是否存在只有颜色、Hover 或 Tooltip 才能理解的信息？
10. 是否新增了长期维护成本或新的样式覆盖链？

代码评审时依次确认：

1. Surface 是否通过 SurfaceManager 打开和关闭？
2. 是否保留 DOM、ARIA 和事件契约？
3. 是否使用 Token，是否新增魔法值？
4. 是否绕过 Primitive 创建了相似组件？
5. 是否存在不必要的 ID 选择器、深层嵌套或 `!important`？
6. 是否补充了状态、焦点和响应式测试？
7. 是否完成浏览器实际界面验证？

---

本规范的目标不是让所有界面看起来完全相同，而是让所有界面像同一套舰桥系统中的不同工作站：共享基础语言、状态和交互规则，同时保留市场、机库、档案和星图各自的任务特征。
