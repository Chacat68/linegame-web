# 星际贸易商 - 技术架构设计（当前实现版）

> 更新日期：2026-08-21
> 判定基准：以当前仓库 `js/`、`ui/`、`tests/` 的实际接线为准，而不是早期泛化设计稿。
> 当前版本定位：浏览器单机版，Vanilla JavaScript + ES Modules，Vite 负责开发与生产构建，Three.js 负责主 3D 星图，Canvas 2D 提供降级渲染。

---

## 1. 技术基线

当前项目的运行时基线已经比较明确：

- 运行环境：浏览器静态页面，无服务端依赖
- 语言与模块：Vanilla JavaScript + ES Modules
- 渲染：Three.js 3D 星图 + Canvas 2D 降级 + DOM/CSS 业务界面
- 开发与构建：Vite
- 状态管理：`GameManager.js` 持有单一运行时 `_state`
- 数据定义：`js/data/*.js` 以模块常量形式提供
- 持久化：`localStorage` 多槽位存档
- 测试：Vitest 单元测试 / 集成测试

当前仓库 **没有** 以下基础设施：

- TypeScript 编译链
- 独立 ResourceManager / 音频资源管理与背景音乐调度（当前仅有轻量短音效 `AudioManager.js`）
- 网络同步层 / 云存档层
- i18n 运行时服务
- 账号体系与后端 API

这不是典型的 MVC，也不是多层服务端架构；更准确的说法是：

**单一状态对象 + 多个纯业务系统 + 由 GameManager 统一编排的前端单机架构。**

## 3. 初始化流程

启动路径非常直接：

1. `js/main.js` 在页面 `load` 事件中调用 `GameManager.init()`，并等待场景 ready promise 后关闭启动层。
2. `StartupState` 解析新档或自动存档；`GameSessionLifecycle.begin()` 统一执行 stop → session replace → `GameSystemRuntime.restore()`。
3. `GameFeatureRuntime` 从 manifest 建立按需功能端口，系统恢复后同步已加载 Feature；市场、舰队、档案、设置等重模块不进入首屏静态依赖图。
4. `GameUiApplicationRuntime` 延迟组装 MarketWorkspace、Settings、GameUiCoordinator、GameUiLifecycle 与 Context adapters，并绑定 eager UI 壳；导航协议由 `GameUiNavigationPort` 独占，顶层只读快照由 `GameUiApplicationDiagnostics` 纯组合。Navigation 的 canonical workspace/L4 栈、Workspace Surface 的唯一可见 DOM 一致性、共享 L4 的投影状态、SurfaceManager 的 Blocking/Escape 仲裁、Context Inspector 的 workspace/renderer/context 计数以及 Event UI 的 pending/Surface 生命周期均直接读取各自 owner，不建立第二份状态，也不泄漏领域对象、回调或 DOM。
5. `GameSessionLifecycle.present()` 统一同步星图/Renderer 投影、增量渲染、恢复待处理事件与 recurring task，再启动 `GameLoopRuntime`；它组合 `GameClockController`、场景帧、延迟功能暂停和领域日推进。
6. `StarmapRenderer.whenSceneReady()` 只在 Three 首帧或 2D 回退帧完成后兑现，避免加载层提前消失。

应用实例退出与 HMR 不复用会话 transition，而由 `GameApplicationLifecycle.shutdown()` 按 Session → Loop → 异步 controller → UI/Context → Feature → Renderer → Runtime Graph 的反向依赖顺序释放；bfcache `pagehide` 不提前销毁同一 JS 实例。

当前初始化链的特点是：

- 顺序仍是显式编排，但 state/session、system restore、Feature、UI 应用层与 game loop 已有独立 runtime 边界。
- 业务系统大多以模块函数形式暴露 `init()`、`advanceDay()`、`handleX()` 等接口。
- UI 层需要的 command 由生命周期/协调器注入，而不是 UI 直接修改全局状态；例如长期路线选择由 `VictoryRuntimeController` 提交，`FleetUI` 以请求对象接收 state 和单一 typed command 端口，船员名单 DOM、危险解雇确认和安全刷新由 `FleetCrewController` 独占；自动跑商则由 `FleetDispatchSession` 独占草案/计数，`FleetDispatchViewAdapter` 独占 `dispatch-*` DOM、表单投影与处理器释放，`FleetDispatchController` 只编排推荐、估算、确认/取消、Surface 与命令提交。任务候选焦点由 `QuestWorkspaceSession` 独占，首页/路线/目标/详情由四组纯 Presenter 投影，根节点委托、放弃确认、阻塞恢复与 generation-safe 焦点提交只由 `QuestBoardController` 协调，`QuestUI` 只组合这些端口；科研总览/候选/队列、补给建议和 Context/L4 由三组纯 Presenter 投影，两个交互根、队列动作与 generation-safe 清空确认只由 `ResearchBoardController` 协调，`ResearchUI` 同样只负责组合；设置入口与延迟加载永久由 `SettingsUiController` 持有，控件/摘要由 `SettingsViewPresenter` 纯投影，分页/控件/危险确认/释放由 `SettingsModalController` 独占，`SettingsManager` 只组合兼容 API，`SettingsCommandController` 独占 settings mutation、持久化、Renderer/Audio 投影与难度/时钟通知。Market 通过 `market-chrome` / `market-spot` / `market-capital` / `market-operations` 区分真实 render port；`MarketWorkspaceSession` 持有内容选择/图表/排序，`MarketWorkspaceEntrySession` 单独持有打开状态、浏览地点和一次性 focus。Fleet 动作区分 `fleet-hangar` / `fleet-shop`；Archive 五页也拥有独立区域。Map 会话只保存局部选择/披露区/航线焦点，Logs 会话保存历史/未读/筛选/聚合；Archive/Fleet Tab 统一由 `WorkspaceTabController` 投影。对象级操作使用 local-scope `WorkspaceActionSlot`，不会发布全局下一步。内部区域仅在所属工作区活动时渲染，隐藏工作区不后台重绘；五个 canonical workspace diagnostics 由协调器只读透传，会话 reset 与 Feature dispose 统一清理选择、表单、日志和详情 surface。
- 存档终端由 `SaveWorkspacePresenter` 纯投影安全状态、槽位、迁移区和危险确认描述；`SaveWorkspaceController` 是容器事件、保存/读取/删除确认、文件输入、Blob 下载、异步读取失效、重绘后焦点恢复与释放的唯一 owner。删除后聚焦同槽位的新保存动作，成功导入后聚焦同槽位的读取动作；若目标离开设置主滚动区则只执行 nearest 回显。保存/读取 intent 由 `SaveCommandAdapter` 规范化为冻结 `SaveCommand`，再由 `GamePersistenceController.handleCommand` 执行；删除与文件迁移仍是 Controller 本地 effect。`SaveUI` 只接收 `{ state, onCommand }` 请求对象，Feature dispose 与会话 reset 都必须释放其交互状态。`css/save-workspace.css` 是存档私有选择器的唯一 CSS owner，并在全局壳层之后加载；其他生产样式不得重新声明 `.save-*`、`#save-list`、`.settings-save-shell` 或存档迁移按钮。
- Context Inspector 由 `ContextInspectorSession` 保存不可变 context key、每工作区开合偏好与 revision，`ContextInspectorPresenter` 只生成壳层和空态，`ContextInspectorViewAdapter` 独占 DOM 根节点、ARIA、工作区宿主、事件委派和焦点恢复，`ContextInspectorController` 只编排 latest-state renderer/action、Session、Escape 注册、响应式开合与冻结 diagnostics；`ContextInspector.js` 仅保留旧 API 兼容组合，不缓存领域对象或读取 DOM。Controller diagnostics 只公开 workspace 标识、计数和布尔状态；`NavigationController.getSnapshot()`、`WorkspaceSurfaceController.getSnapshot()`、`WorkspaceDetailSurface.getSnapshot()`、`SurfaceManager.getDiagnostics()` 与 `EventUI.getDiagnostics()` 分别公开冻结的 L3/L4 状态、DOM 一致性、共享详情投影、Blocking/Escape 仲裁及事件 pending/Surface 生命周期，均由 `GameUiApplicationDiagnostics` 汇入顶层快照。
- UI 刷新由三个边界组合：`GameUiCoordinator` 只解释 dirty region、确保/重置延迟 Feature 并组合 diagnostics；`GameUiWorkspaceRenderer` 构造 Market/Fleet/Archive/Save 区域请求、连接 Context adapter 和注入 typed command；`GameUiRenderSession` 只记录成功区域、刷新事务、全量/失效次数，不读取 state、DOM 或 Feature。

## 4. 状态管理与契约

### 4.1 单一状态源

运行时游戏状态由 `js/core/GameManager.js` 的 `_state` 持有。  
多数系统函数接收 `state` 作为参数并在其上做同步修改。

这种方案的优点是：

- 当前项目规模下调试路径清晰
- 存档序列化简单
- 测试可以直接构造状态对象
- 各系统之间共享上下文成本低

当前的代价是：

- `GameManager` 体积较大，承担了过多编排责任
- 某些流程需要严格遵守调用顺序
- 模块间仍然存在一定的隐式耦合

### 4.2 状态结构唯一来源

`js/data/constants.js` 是状态结构与持久化契约的唯一真理来源，主要包括：

- `SAVE_STATE_SCHEMA`
- `SAVE_META_SCHEMA`
- `RUNTIME_ONLY_FIELDS`
- `createInitialState()`
- `createPersistedState()`
- `INITIAL_STATE`

这意味着：

- 新增持久化字段时，必须更新 `SAVE_STATE_SCHEMA`
- 新增 `meta` 字段时，必须更新 `SAVE_META_SCHEMA`
- 运行时字段若不该入档，必须加入 `RUNTIME_ONLY_FIELDS`
- 任何文档描述都应以这些定义为准

### 4.3 状态变更入口

当前项目的主要状态变更入口集中在：

- `GameManager` 的 `_handleTravel`、`_handleOpenBuy`、`_handleOpenSell` 等动作函数
- 各系统模块导出的业务函数，例如 `Trade.travelTo()`、`Finance.takeLoan()`、`Quest.completeQuest()`
- `CommerceFacade` 提供的统一商业动作封装

总体原则是：

- UI 负责触发动作
- `GameManager` 负责调度
- `systems/*` 负责业务规则
- `_updateUI()` 在状态变更后统一刷新视图

## 5. 核心系统职责

### 5.1 经济与贸易

- `Economy.js`：供需、价格漂移、价格历史、经济周期、黑市、走私检查
- `TradeSystem.js`：买入、卖出、加油、旅行、跨星系移动

- `FinanceSystem.js`：贷款、保险、股票、本地投资、信用评级
- `FuturesSystem.js`：期货合约、多空仓、保证金、结算
- `CommerceFacade.js`：给 `GameManager` 提供统一商业操作入口

当前商业终端已经不是单纯市场页，而是把：

- 现货交易
- 资本操作
- 贸易站经营

整合到 `MarketUI.js` 的统一“商业终端”内。`MarketUI` 只保留四个具名增量 render port 和 controller 编排，行情图表、现货摘要、商品卡、资金、贸易站与商品详情投影分别由 `MarketChartPresenter`、`MarketSpotPresenter`、`MarketGoodsPresenter`、`MarketCapitalPresenter`、`MarketOperationsPresenter`、`MarketCommodityDetailPresenter` 拥有；`MarketChromeController` 独占顶部 Chrome、详情地点/市场模式和引导高亮/滚动/动作落点，动态地点字段进入 HTML 前统一转义。`MarketSpotController` 统一解析公开/黑市商品快照，并组合现货外壳、各地价格总览、商品列表、图表、分析面板和远程地点/局部重绘回调。行情图表内部再分三层：`MarketChartPresenter` 只生成价格序列、SVG 和冻结 Dashboard/K-line view model，`MarketChartViewAdapter` 独占六个 DOM 区域、Dashboard/K-line 单根 click 委托、滚动同步与 reset 解绑，`MarketChartController` 只解释共享商品焦点、统计窗口和两视图局部重绘。`MarketGoodsController` 独占商品工具栏、列表、快速交易和 typed command 转换，两者只通过同一个 `MarketSelectionController` 读写商品焦点、发布 Context 并请求 `market-spot` 局部重绘。`MarketFinanceController` 独占资金/贸易站稳定容器、二级菜单绑定、全部融资/经营 typed command、经营排序局部重绘和按渲染周期共享的 Commerce 快照；`MarketCommodityController` 独占商品 Context/L4 的地点、市场模式、价格、供需、库存与现金解析及容器写入，四个区域控制器的冻结 diagnostics 都经 `MarketUI` 汇总。商品卡与行情榜因此始终共享选中状态；经营排序只重绘贸易站区，重复或非法排序不产生重绘。交易、融资和有成本经营通过动作影响矩阵同步现金相关区域，纯策略切换只失效经营区。`MarketCommand` 冻结 UI / controller 契约，`MarketWorkspaceController` 统一解释买卖、补给、贷款、投资、建站、批量策略和远程航点；商品 Context 通过统一局部 intent 进入 `WorkspaceDetailSurface`，切换远程地点会立即按最新上下文重渲染，Escape 精确返回原入口。`TradeStationUI.js` 目前仅保留为兼容层；商网总览页还承担全网批量投资、升级和策略切换的远程指令入口。

贸易站经营内部继续按信息职责拆分：`MarketOperationsPresenter` 只采集领域快照并组合结果，`MarketBatchPlanPresenter` 独占批量排序、预算覆盖和实际下发清单，`MarketLocalOperationsPresenter` 独占本地可执行/远程只读状态，`MarketOperationsOverviewPresenter` 独占商网指挥台与网络摘要，`MarketTradeStationListPresenter` 独占候选探索情报和候选/已建站列表。

## 6. UI 与渲染架构

### 6.1 星图渲染主线

当前地图渲染入口是 `js/ui/StarmapRenderer.js`。它统一维护渲染器状态，并在 Three.js 主线与 Canvas 2D 降级路径之间切换。

它负责：

- 优先按需加载 `RendererThreeStarmap.js`，使用 Three.js 渲染 3D 星图
- WebGL2 不可用或 Three.js 尚未就绪时使用 `Renderer2DStarmap.js`
- 本地开发可使用 `?starmap=2d` 稳定验收完整降级路径；该开关只在 Vite `DEV` 模式生效
- 星球 / 星系视图切换
- 飞船飞行动画
- 派遣航线可视化
- 与设置中的动画 / 显示偏好联动

`Renderer3DAdvanced.js` 的 Babylon.js 实现仍保留在仓库中，但已不是 `GameManager` / `MapUI` 的运行时入口；当前文档与新功能应以 `StarmapRenderer.js` 契约为准。

### 6.2 UI 组织方式

UI 模块以功能面板拆分，常见模式是：

- `init(state, callbacks...)`
- `render(state, ...)`
- 根据 DOM id 直接更新片段

当前关键界面包括：

- `GameShellProjection.js`：一次刷新事务组合 Header、公司经营、Archive 角标与长期路线摘要；`GameUiCoordinator` 只依赖该 typed port
- `HUD.js`：只保留 Shell 交互生命周期、长期路线 command 与通讯日志端口，不再持有全局信息投影
- `HeaderStatusPresenter.js`：纯投影信用点、位置、日期、当前舰船、声望与舰船资源 meter；星图工具只发布绑定就绪信号
- `CompanyOverviewPresenter.js`：把 Header 公司身份与机库净资产、等级、容量/权限详情投影到各自唯一位置
- `ArchiveBadgePresenter.js`：从任务、探索、科研、派系和成就 selector 构造冻结角标快照，并只投影六个声明式 badge
- `HudInteractionController.js`：独占 HUD 的 EventBus/DOM listener、长期路线弹层、星图工具、Context `900px` 断点监听和 dispose/re-init；断点 listener 必须随 HUD 生命周期完整释放
- `VictoryProgressPresenter.js`：纯渲染长期路线摘要与详情，统一转义领域内容
- `MapUI.js`：组合星图会话、视图状态、Context、面板、导航、交互与探索详情 controller；公开导航 API 只做薄转发，不再访问 document、解析详情根节点、解释星系/星球切换、旅行分发、引导聚焦、Renderer 对焦，也不再直接注册全局回调、EventBus、DOM listener 或导出市场/通用 Tab API
- `MapGalaxyHubPresenter.js`：星系总览解锁/访问/贸易线索模型、HTML 和单一跃迁 intent
- `MapViewStateController.js`：星系/星球视图切换、当前查看星系与悬停目标的唯一状态写入边界
- `MapExplorationPresenter.js`：POI 状态组合、探索流程模型、HTML 与稳定探索 intent
- `MapPlanetDetailPresenter.js`：星球摘要、局部航线焦点、路线估算、探索组合与 travel intent
- `MapPanelLayout.js`：根据容器、Renderer 坐标、面板高度和 Command Slot 净空计算冻结几何模型

- `MapPanelViewController.js`：独占星系/星球面板 DOM、ARIA、滚动保留、Renderer 锚点测量与 Command Slot 净空样式投影
- `MapContextController.js`：独占地图 Context key、Renderer selection、Context renderer 注册与地图对象 Escape layer
- `MapInteractionController.js`：独占 Renderer 全局回调、星系视图 EventBus 订阅、面板 DOM listener 收集和逆序释放；长期回调始终读取 latest-state provider
- `MapNavigationController.js`：独占注入式工作区请求、星系/星球视图切换、同/跨星系旅行分发、引导目标聚焦、Context/面板刷新与 Renderer 对焦；reset 保留 wiring，dispose 清空动作端口

- `FleetSurfaceCoordinator.js`：独占 inline/blocking Surface 判定、Portal 构造、危险确认只读上下文、统一关闭/reset 与冻结 diagnostics；Crew/Mod/Dispatch 只消费它的窄 Surface 端口
- `FleetInlinePortalController.js`：独占机库内联二级界面的 modal box 归还、ARIA/inert、滚动归零/恢复、Escape、返回按钮与焦点恢复生命周期
- `FleetShipDetailController.js`：组合 Fleet/Crew selector 与两组纯 Presenter，独占舰船 Context Inspector/L4 宿主投影和冻结诊断

- `FleetHangarController.js`：独占查看舰选择、机库根 DOM 委托、Context 同步、重绘后焦点、Crew/Mod/Dispatch 窄入口与冻结 diagnostics；reset 必须解绑自己持有的处理器
- `FleetShopPresenter.js`：船坞采购评分、预算/席位信号、船卡 HTML 和单一购买 intent 协议
- `FleetShopController.js`：独占采购根 DOM、购买 intent、采购焦点 diagnostics 与 reset 解绑；只通过 `FleetCommandAdapter` 发布命令

- `FleetCrewController.js`：船员弹层 DOM、单一名单委托、招募/分配/撤下/切船命令、危险解雇确认、generation-safe 延迟刷新和处理器释放；冻结 diagnostics 由 `FleetUI` 汇总

- `FleetModController.js`：改装/保养 DOM、引导焦点、五类 intent、危险售船确认、generation-safe 延迟刷新和处理器释放；冻结 diagnostics 由 `FleetUI` 汇总

## 7. 存档与数据持久化

### 7.1 当前存档方案

存档系统由 `js/systems/save/SaveSystem.js` 提供，当前方案为：

- 介质：`localStorage`
- 槽位：4 个（0 自动存档，1-3 手动存档）
- 结构：`SaveEnvelope = { meta, data }`
- 版本：`SAVE_SCHEMA_VERSION = 17`
- 游戏版本字段：`GAME_VERSION = 0.6.4`

### 7.2 当前已实现能力

- 存档保存 / 读取
- 槽位列表与损坏槽位识别
- JSON 导入 / 导出
- schema 迁移
- 运行时字段剔除
- 存档摘要信息生成
- 星系探索状态迁移与恢复
- 中期专题教学链状态的迁移、嵌套规范化与恢复

### 7.3 当前未实现能力

- IndexedDB 存档
- 云存档 / 多端同步
- 账号绑定档案

因此文档里如果提到 IndexedDB、账号云档或服务端同步，必须明确为**远期规划**，不是现状。

## 10. 文档口径建议

对外描述当前项目时，建议统一使用以下表述：

1. 这是一个浏览器单机星际贸易经营游戏。
2. 当前主干实现基于 `GameManager` 单一状态编排，而不是服务端驱动架构。
3. 当前商业、舰队、任务、金融、贸易站、研究、成就、胜利、存档都已接入主流程。
4. 探索 MVP、行动引导和统一命令 CTA 已接入主流程，后续重点是中期经营联动。
5. 基础短音效已接入现版本；背景音乐、音频资源包、动态音乐、国际化、云存档、多人属于后续平台能力。
6. `StarmapRenderer.js`、`MarketUI.js`、`MapUI.js`、`UIManager.js` 与 `ActionGuideUI.js` 分别是地图渲染门面、商业终端、星图交互、全局视图管理和行动引导的真实运行时入口。

这份文档的目标不是给未来所有可能形态预留想象空间，而是让开发者在打开仓库后，能立刻理解**当前代码到底怎么跑**。
