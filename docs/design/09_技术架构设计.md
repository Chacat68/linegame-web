# 星际贸易商 - 技术架构设计（当前实现版）

> 更新日期：2026-08-13
> 判定基准：以当前仓库 `js/`、`ui/`、`tests/` 的实际接线为准，而不是早期泛化设计稿。
> 当前版本定位：浏览器单机版，Vanilla JavaScript + ES Modules，Vite 负责开发与生产构建，Three.js 负责主 3D 星图，Canvas 2D 提供降级渲染。

---

## 1. 技术基线

当前项目的运行时基线已经比较明确：

- 运行环境：浏览器静态页面，无服务端依赖
- 语言与模块：Vanilla JavaScript + ES Modules
- 渲染：Three.js 3D 星图 + Canvas 2D 降级 + DOM/CSS 业务界面
- 开发与构建：Vite
- 状态管理：`GameManager.js` 持有单一运行时 `_state`
- 数据定义：`js/data/*.js` 以模块常量形式提供
- 持久化：`localStorage` 多槽位存档
- 测试：Vitest 单元测试 / 集成测试

当前仓库 **没有** 以下基础设施：

- TypeScript 编译链
- 独立 ResourceManager / 音频资源管理与背景音乐调度（当前仅有轻量短音效 `AudioManager.js`）
- 网络同步层 / 云存档层
- i18n 运行时服务
- 账号体系与后端 API

## 2. 目录分层

当前目录结构以“核心调度 + 数据模块 + 系统模块 + UI 模块”组织：

```text

    SettingsManager.js     # 设置弹窗与配置读写
    DispatchController.js  # 派遣流程与运行态调度
  data/
    constants.js           # 状态结构、配置常量、存档契约唯一真理来源
    goods.js               # 商品定义

    ships.js               # 船型、改装、席位、舰队加成

    faction/               # 派系关系与黑市权限
    research/              # 科技研究
    quest/                 # 任务推进

    galaxy/                # 星系数据层
```

这不是典型的 MVC，也不是多层服务端架构；更准确的说法是：

**单一状态对象 + 多个纯业务系统 + 由 GameManager 统一编排的前端单机架构。**

## 3. 初始化流程

启动路径非常直接：

1. `js/main.js` 在页面 `load` 事件中调用 `GameManager.init()`。
2. `GameManager` 基于 `INITIAL_STATE` 深拷贝生成运行态，并读取设置与难度。
3. 依次初始化经济、舰队、派系、研究、任务、成就、贸易站、金融、星系数据层。
4. 初始化 `StarmapRenderer`、`HUD`、`MapUI`、`MarketUI`、`UIManager`、`ActionGuideUI` 相关回调；Three.js 模块按需加载，首帧可先由 2D 渲染器承接。
5. 初始化教程系统、行动建议、设置弹窗、公司改名弹窗等附加流程。
6. 调用 `_updateUI()` 完成首屏渲染，再启动游戏循环。

当前初始化链的特点是：

- 顺序强依赖明显，属于“显式编排”而不是自动依赖注入。
- 业务系统大多以模块函数形式暴露 `init()`、`advanceDay()`、`handleX()` 等接口。
- UI 层需要的回调由 `GameManager` 注入，而不是 UI 直接修改全局状态。

## 4. 状态管理与契约

### 4.1 单一状态源

运行时游戏状态由 `js/core/GameManager.js` 的 `_state` 持有。  
多数系统函数接收 `state` 作为参数并在其上做同步修改。

这种方案的优点是：

- 当前项目规模下调试路径清晰
- 存档序列化简单
- 测试可以直接构造状态对象
- 各系统之间共享上下文成本低

当前的代价是：

- `GameManager` 体积较大，承担了过多编排责任
- 某些流程需要严格遵守调用顺序
- 模块间仍然存在一定的隐式耦合

### 4.2 状态结构唯一来源

`js/data/constants.js` 是状态结构与持久化契约的唯一真理来源，主要包括：

- `SAVE_STATE_SCHEMA`
- `SAVE_META_SCHEMA`
- `RUNTIME_ONLY_FIELDS`
- `createInitialState()`
- `createPersistedState()`
- `INITIAL_STATE`

这意味着：

- 新增持久化字段时，必须更新 `SAVE_STATE_SCHEMA`
- 新增 `meta` 字段时，必须更新 `SAVE_META_SCHEMA`
- 运行时字段若不该入档，必须加入 `RUNTIME_ONLY_FIELDS`
- 任何文档描述都应以这些定义为准

### 4.3 状态变更入口

当前项目的主要状态变更入口集中在：

- `GameManager` 的 `_handleTravel`、`_handleOpenBuy`、`_handleOpenSell` 等动作函数
- 各系统模块导出的业务函数，例如 `Trade.travelTo()`、`Finance.takeLoan()`、`Quest.completeQuest()`
- `CommerceFacade` 提供的统一商业动作封装

总体原则是：

- UI 负责触发动作
- `GameManager` 负责调度
- `systems/*` 负责业务规则
- `_updateUI()` 在状态变更后统一刷新视图

## 5. 核心系统职责

### 5.1 经济与贸易

- `Economy.js`：供需、价格漂移、价格历史、经济周期、黑市、走私检查
- `TradeSystem.js`：买入、卖出、加油、旅行、跨星系移动
- `AutoTradeSystem.js`：自动贸易策略与路线评估
- `TradeStationSystem.js`：建站、升级、经理、策略、收益结算

### 5.2 金融与经营

- `FinanceSystem.js`：贷款、保险、股票、本地投资、信用评级
- `FuturesSystem.js`：期货合约、多空仓、保证金、结算
- `CommerceFacade.js`：给 `GameManager` 提供统一商业操作入口

当前商业终端已经不是单纯市场页，而是把：

- 现货交易
- 资本操作
- 贸易站经营

整合到 `MarketUI.js` 的统一“商业终端”内。`TradeStationUI.js` 目前仅保留为兼容层，真实运行时入口已经统一收口到 `MarketUI.js`；商网总览页还承担全网批量投资、升级、经理派驻和策略切换的远程指令入口。

### 5.3 舰队、船员与派遣

- `FleetSystem.js`：多船管理、买卖船、切换激活船、改装、派遣航线
- `CrewSystem.js`：招募、分配、成长、船员市场
- `DispatchController.js`：派遣运行态与渲染联动

### 5.4 成长、任务与世界状态

- `FactionSystem.js`：派系关系、税率修正、黑市访问条件
- `ResearchSystem.js`：科技研究、队列与效果落地
- `QuestSystem.js`：章节任务、前置条件、推荐任务
- `AchievementSystem.js`：成就检测与奖励
- `ProgressionSystem.js`：玩家等级 / 公司等级成长
- `RandomEvent.js`：事件概率、冷却、阶段节奏、事件链
- `GalaxyDataLayer.js`：星球运行时状态与星系数据层
- `ExplorationSystem.js`：POI 调查、秘密航线、勘探报告、经营决策情报
- `GuidanceSystem.js`：根据状态和 UI context 输出唯一当前行动建议
- `GuidanceActionController.js`：将行动建议 actionType 分发到 `GameManager` 注入的执行回调
- `MidgameTeachingChain.js`：中期专题链定义与优先级逻辑；当前仍缺运行时启动、真实动作完成事件和持久化，不能视为完整运行时能力
- `VictorySystem.js`：多路径胜利判定与进度
- `TutorialSystem.js`：分步教程与新手引导

## 6. UI 与渲染架构

### 6.1 星图渲染主线

当前地图渲染入口是 `js/ui/StarmapRenderer.js`。它统一维护渲染器状态，并在 Three.js 主线与 Canvas 2D 降级路径之间切换。

它负责：

- 优先按需加载 `RendererThreeStarmap.js`，使用 Three.js 渲染 3D 星图
- WebGL2 不可用或 Three.js 尚未就绪时使用 `Renderer2DStarmap.js`
- 星球 / 星系视图切换
- 飞船飞行动画
- 派遣航线可视化
- 与设置中的动画 / 显示偏好联动

`Renderer3DAdvanced.js` 的 Babylon.js 实现仍保留在仓库中，但已不是 `GameManager` / `MapUI` 的运行时入口；当前文档与新功能应以 `StarmapRenderer.js` 契约为准。

### 6.2 UI 组织方式

UI 模块以功能面板拆分，常见模式是：

- `init(state, callbacks...)`
- `render(state, ...)`
- 根据 DOM id 直接更新片段

当前关键界面包括：

- `HUD.js`：资源、阶段、成长与胜利进度
- `MapUI.js`：星图交互、市场入口、视图切换
- `MarketUI.js`：现货 / 资本 / 经营三合一商业终端
- `FleetUI.js`：船只、改装、船员、派遣
- `UIManager.js`：底栏视图切换、大面板互斥、日志 modal 与星图背景模糊
- `ActionGuideUI.js`：非阻塞当前行动条
- `CommandAction.js`：统一 CTA 的 surface / intent / verb 元信息和执行反馈
- `QuestUI.js`、`ResearchUI.js`、`FactionUI.js`、`SaveUI.js`、`TutorialUI.js`

### 6.3 事件通信

`EventBus.js` 是当前的横向解耦机制，主要用于：

- 日志消息广播
- 教程完成通知
- 某些 UI 层提示与状态同步

它不是完整状态管理库，更像一个轻量的发布 / 订阅工具。

## 7. 存档与数据持久化

### 7.1 当前存档方案

存档系统由 `js/systems/save/SaveSystem.js` 提供，当前方案为：

- 介质：`localStorage`
- 槽位：4 个（0 自动存档，1-3 手动存档）
- 结构：`SaveEnvelope = { meta, data }`
- 版本：`SAVE_SCHEMA_VERSION = 17`
- 游戏版本字段：`GAME_VERSION = 0.6.4`

### 7.2 当前已实现能力

- 存档保存 / 读取
- 槽位列表与损坏槽位识别
- JSON 导入 / 导出
- schema 迁移
- 运行时字段剔除
- 存档摘要信息生成
- 星系探索状态迁移与恢复
- 中期专题教学链状态的迁移、嵌套规范化与恢复

### 7.3 当前未实现能力

- IndexedDB 存档
- 云存档 / 多端同步
- 账号绑定档案

因此文档里如果提到 IndexedDB、账号云档或服务端同步，必须明确为**远期规划**，不是现状。

## 10. 文档口径建议

对外描述当前项目时，建议统一使用以下表述：

1. 这是一个浏览器单机星际贸易经营游戏。
2. 当前主干实现基于 `GameManager` 单一状态编排，而不是服务端驱动架构。
3. 当前商业、舰队、任务、金融、贸易站、研究、成就、胜利、存档都已接入主流程。
4. 探索 MVP、行动引导和统一命令 CTA 已接入主流程，后续重点是中期经营联动。
5. 基础短音效已接入现版本；背景音乐、音频资源包、动态音乐、国际化、云存档、多人属于后续平台能力。
6. `StarmapRenderer.js`、`MarketUI.js`、`MapUI.js`、`UIManager.js` 与 `ActionGuideUI.js` 分别是地图渲染门面、商业终端、星图交互、全局视图管理和行动引导的真实运行时入口。

这份文档的目标不是给未来所有可能形态预留想象空间，而是让开发者在打开仓库后，能立刻理解**当前代码到底怎么跑**。
